## Reproduced defect — `cplus_realloc` leaves the stdlib side table stale

`error.hp` has no `stdlib_realloc` wrapper, so the instructed fallback
`cplus_realloc` is the only realloc entry point available to `.hp` containers.
The linked runtime (`c-plus-core/build/libcplus_runtime.a`) implements
`cplus_realloc` as an ownership transfer: it allocates a fresh managed block,
copies the payload and **releases the old pointer**. The stdlib metadata side
table in `stdlib/error.hp` is not notified by either operation. Consequence:
after `q = cplus_realloc(p, 64)` the old pointer `p` is dead in the runtime but
still has a live 32-byte stdlib metadata record with a valid generation, while
the new pointer `q` has no stdlib metadata at all. `stdlib_release(p)` would
therefore report a stale metadata hit and then be a fatal double free at the
runtime layer; the metadata cannot be used to detect that stale alias.

Characterised (not silently accepted) by `asmi_c_grow_stdlib_defect_old_stale`
and `asmi_c_grow_stdlib_defect_new_untracked`, both of which print `1` in every
mode. The suite cleans up correctly (`stdlib_meta_forget(p)` on the dead alias,
`stdlib_release` only on the live result).

Minimal repro (run from the repository root, same PATH/CPLUS_CLANG as above;
source saved in the temp work directory, not in the repo):

```c
/* abi_repro_realloc.cp */
#include <stdio.h>
#include "cplus/cplus.h"
#include "stdlib/error.hp"
int main(void) {
    void *p = stdlib_alloc(32);
    unsigned long long g = stdlib_alloc_generation(p);
    void *q = cplus_realloc(p, 64);
    print("q_size", stdlib_alloc_size(q));              /* want 64, got 0  */
    print("p_size_stale", stdlib_alloc_size(p));        /* want 0,  got 32 */
    print("p_gen_still_live", stdlib_alloc_check_generation(p, g)); /* want 0, got 1 */
    print("q_runtime_size", cplus_alloc_bytes(q));      /* 64: runtime table is correct */
    stdlib_meta_forget(p);                              /* manual cleanup only */
    stdlib_release(q);                                  /* p must NOT be released */
    return 0;
}
```

```sh
timeout 30 ./build/c+ build "$T/abi_repro_realloc.cp" \
    --strict --sanitize=none -o "$T/abi_repro_realloc"
"$T/abi_repro_realloc"
# build_rc=0, run_rc=0
```

Observed stdout (exact):

```

p_size_stale 32
p_gen_still_live 1
q_runtime_size 64
```

Expected for a metadata-correct `stdlib_realloc`: `q_size 64`,
`p_size_stale 0`, `p_gen_still_live 0`. SafeCRT's `realloc_s` does preserve
metadata (verified by `ass_f_*`, 51/0), so the gap is specific to the
`error.hp` stdlib side table / `cplus_realloc` combination. No header was
edited to work around it.

## Deliberate non-fatal design choices in the suite (not defects)

- A literal second `stdlib_release(stale)` terminates the process with
  `CPLUS_EXIT_DOUBLE_FREE` (104) and `cplus_release` on a stack address with
  `CPLUS_EXIT_TYPE_CONFUSION` (105). Those are fatal-by-design paths, so the
  self-checking suite detects them through side-table queries and the
  non-destructive `stdlib_transfer_ownership` / `free_checked_s` refusal
  APIs instead of invoking them.
- `cplus_realloc(ptr, 0)` and interior pointers are handled exactly as the
  runtime and side tables define them; interior pointers are not tracked by
  `stdlib_alloc_size` (capacity is derived from the recorded base), while
  `cplus_safe_remaining_capacity` does handle them in the SafeCRT layer.
