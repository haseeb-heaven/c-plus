# Hostile-input corpus for stdlib parsers — Task 6 Phase 2

Branch `agent/modern-stdlib`. Compiler `./build/c+` (C+ 0.1.0, Apple clang 16
backend). All commands below were run from the repository root with

```
PATH=/usr/bin:/bin:/usr/sbin:/sbin:/opt/homebrew/bin:$PATH
```

Scope: deterministic, recoverable hostile-input probes for `io.hp`, `file.hp`,
`json.hp`, `fs.hp`, `net.hp` and `string.hp`. No raw UB is generated by a test
outside the operation under test: every probe is an API call with a defined
return/error contract or a metadata query. Strict-safe patterns are used
throughout: unique variable names, named temporaries (one owning resource per
statement), `__builtin_memcpy` for element access through pointer parameters
(including `argv`), no variable division/modulo, and JSON link flags passed as
separate argv operands (`-Ithird_party/yyjson`, `-Lbuild/ext`, `-lyyjson`).

### Mode 2 — UBSan

The canonical `./build/c+ build <src> --strict --sanitize=undefined` form is
**BLOCKED on this host by a pre-existing toolchain defect** (see §4). To still
obtain UBSan evidence for the parsers, `run.sh` keeps `--sanitize=none` (so the
C+ runtime link succeeds) and appends Clang UBSan flags after `--`:

```
./build/c+ build tests/security/hostile_inputs/<name>.cp --strict --sanitize=none \
    [JSON_FLAGS] -o "$OUT/<name>_ubsan" -- -fsanitize=undefined -fno-sanitize-recover=all
timeout -k 5 30 "$OUT/<name>_ubsan" tests/security/hostile_inputs/fixtures
```

The lowered translation unit includes the `stdlib/*.hp` headers, so the parser
code itself is instrumented. The produced binaries link
`libclang_rt.ubsan_osx_dynamic.dylib` and import `__ubsan_handle_*` (verified
with `otool -L` / `nm -g`). All four UBSan runs exited 0 with **zero stderr
bytes**: no UBSan diagnostic was emitted for any hostile input. The C+ runtime
library is not instrumented by this workaround; that limitation is recorded,
not hidden.

## 4. Defects / findings

1. **Toolchain defect (BLOCKED canonical UBSan), pre-existing, high impact on
   verification.** `./build/c+ build <any>.cp --strict --sanitize=undefined`
   fails while rebuilding the C+ runtime:
   `/Users/haseeb-mir/.../c-plus-core/runtime/cplus_runtime.c:129:23: error:
   use of undeclared identifier 'CPLUS_EXIT_ARITHMETIC'`. Reproduced with an
   untouched existing test (`tests/stdlib/deep_io_1byte.cp`), so it is not
   caused by this corpus. Consequently the canonical UBSan mode could not be
   executed; parser-level UBSan evidence was obtained via the post-`--`
   Clang-flag workaround described in §2. This belongs to the compiler/runtime
   integration, not to any `stdlib/*.hp` parser.

2. **`net.hp::is_valid()` reports numeric-range validity, not descriptor
   liveness (robustness/API-semantics finding, low severity).**
   `connection_borrow(999999).is_valid()` returns 1 even though the descriptor
   is not open; the same handle's `read`/`write` correctly return
   `STDLIB_FAIL` with `STDLIB_CATEGORY_IO`. `listener_borrow(999999)` behaves
   the same (`is_valid() == 1`, `bound_port() == 0`). The checks
   `net_conn_bogus_is_valid` and `net_listener_borrow_bogus_is_valid` pin this
   observed behaviour as metadata; callers must not treat `is_valid()` as proof
   that I/O will succeed.

3. **Zero-length `connection::write` succeeds on a non-open descriptor
   (low severity, documented observation).** `connection_borrow(999999).write(buf, 0, &e)`
   returns `STDLIB_OK` because the loop issues no syscall. The check
   `net_conn_zero_len_write` records this; it is not a crash or UB.

4. **`json.hp` parses only the NUL-terminated prefix of a buffer (contract
   behaviour, not a defect).** `json("{\"a\":1}\0{\"b\":2}")` yields a valid
   document with `size()==1` and no member `"b"`. This follows from the header
   using `strlen(text)`; recorded so callers feeding byte buffers know the
   truncation rule.

No crashes, hangs, out-of-bounds accesses, allocator aborts or UBSan reports
were observed for any of the 143 hostile-input checks in either executed mode.
