## 3. Detailed technical rationale

### 3.1 safeclib — USE (primary checked backend)
- Exactly one pinned revision: `90b076e94c4b0fb202dddf948d5d620e5395c1b0`, MIT.
- Integration is a **subset**, not the whole repository: 18 upstream sources plus a local adapter, selected by `scripts/build_safecrt.sh`. This keeps the dependency closure small (private headers, mem primitives, two constraint handlers, generated `config.h`) and avoids the 188 uncompiled `.c` files.
- Symbol collisions are prevented at build time with `-Dname=cplus_sc_name`; the Intel backend is explicitly not compiled. This is the key reason two checked-C libraries can coexist in `third_party/` without coexisting in the link.
- Local correctness/security work is recorded and tested: `strtok_s` trailing-token/empty-input handling, `src/cplus_sc_wrappers.c` 5-arg adapter, and the `strnlen_s` guard-order security patch verified by UBSan/canaries and `tests/crt/adversarial/test_memory_attack.c`.
- Caveat: `_s` names imply runtime constraint checks only; ownership, lifetime, provenance, aliasing and races remain unproven. `docs/libc/CPLUS_RUST_CONFORMANCE.md` states C+ is **not** Rust-equivalent.

### 3.2 Intel safestringlib — REFERENCE ONLY
- Pinned SHA `f4491915cc682556ed64d4eb6a2461d8eed2eb0c` exists in `PROVENANCE.md` and the license doc, but there is **no `UPSTREAM_COMMIT` file** — a traceability weakness to fix if the reference copy is kept.
- `scripts/build_safecrt.sh` contains the comment "Intel safestringlib retained … for provenance/reference only; not compiled/linked." Consequently no local test exercises it, and its 6 copied unit tests are inert.
- Linking it would reintroduce the same exported names as safeclib; `rename_symbols.h` is a contingency, not a current mitigation. Keeping one active backend is the safer engineering choice.
- The "archived upstream" characterization comes from the assignment; it is **not** corroborated by any local file. Do not restate it as locally verified.

### 3.3 musl — USE selectively
- Exactly one pinned revision `7813e9119eb5fe681b6750b8a033a0490bca0941`, MIT, `COPYRIGHT` preserved.
- Local copies are renamed and integrated (`cplus_memccpy`, `cplus_stpcpy`, `cplus_div`, `cplus_isascii`, etc.); math and `strtod`-family code is platform-backed, not musl-derived. This avoids a second allocator/libc and host CRT symbol clashes.
- `libc/upstream/musl/PROVENANCE.md` mentions `src/malloc/* (malloc.c etc. as present)` but the tree contains only `calloc.c`, `free.c`, `realloc.c` — the provenance text is broader than the actual copy. Treat the file list, not the prose, as authoritative.
- Approved scope is the recorded subset only; no wholesale musl import.

### 3.4 CTL — container component, not libc
- Pinned `ede5f455392f2380dd16aead26835eece6cd20e4`, MIT, header-only.
- Explicitly **not** a libc implementation: it provides typed containers (`vector`, `string`, `map`, …) and consumes libc headers; it cannot satisfy any libc function or CRT contract.
- Local hardening in `vector.h` and `string.h` is documented; `tests/ctl/` provides regression coverage.

### 3.5 LLVM libc — evaluate, do not vendor
No files were copied. Reasons, each independently sufficient:
1. **No pinned revision** exists locally, so adoption would violate the pin-exact-revision rule until a SHA is deliberately chosen and recorded.
2. **C++/LLVM build requirement**: `libc/CMakeLists.txt` is a C99 project with no LLVM tooling; LLVM libc needs generated headers, CMake infrastructure and a C++ toolchain.
3. **Dependency closure / platform assumptions**: target-specific overlays and generated configuration are far larger than this project's selectable subsets.
4. **Symbol risk**: a libc copy would redefine host CRT entry points, which local policy forbids.
Value retained is methodological only (precondition/bounds patterns, differential testing in `tests/libc/test_differential_libc.c`).

### Why no candidate substitutes for Rust-style lifetimes
`docs/LANGUAGE.md` ("Borrowing") and `docs/LIMITATIONS.md` record that C+ implements a targeted borrow subset: "no lifetime annotations, no aliasing/exclusivity rules, and no field-level or container-level tracking"; full Rust-style borrow checking is **not implemented**. `docs/libc/CPLUS_RUST_CONFORMANCE.md` explicitly states C+ is not Rust-equivalent. Checked `_s` APIs (safeclib), selective primitives (musl), and containers (CTL) operate at runtime/API level: they cannot prove caller ownership, lifetime or provenance. Therefore library selection cannot close the lifetime gap; that belongs to the compiler/runtime work tracked in `docs/UPSTREAM_AUDIT.md` and `docs/LIMITATIONS.md`.

## 5. Why we do not copy entire repositories blindly

1. **License correctness**: a full copy imports every license, generated table, test fixture and data file, multiplying the notices that must be preserved (e.g. safeclib's MIT + embedded notices, Intel's dual Intel/Cisco MIT notices, musl's large contributor list). MIT compatibility here is established per component, not per repository blob.
2. **Provenance and pinning**: whole-repo drops obscure what exact revision was used and which files were changed. The adopted components each have an exact SHA plus a `PROVENANCE.md` listing local adaptations; a blind copy would break that chain and make the local security patches (`strnlen_s`, `strtok_s`, CTL guards) impossible to distinguish from upstream.
3. **Dependency closure / attack surface**: safeclib's 206 sources vs 18 compiled; musl's full libc vs 40 selective files; LLVM libc's generated/target-specific tree vs C99 project. Uncompiled code still carries audit and license obligations.
4. **Symbol and ABI collisions**: host CRT and second-backend collisions are real (`memcpy_s`, `strcpy_s`, `malloc`). Prefixing (`cplus_sc_*`), renaming (`cplus_*`), and one-backend-at-a-time linking are deliberate controls that a blind copy would bypass. `docs/ROADMAP.md` forbids a separate CRT package / glibc fork / global libc replacement.
5. **Platform assumptions**: musl is Linux-oriented, Fil-C is Linux/x86-64 + GC, LLVM libc requires a C++ toolchain and per-target config; none matches the "reuse existing toolchain, preserve native C ABI" constraint without selective adaptation.
6. **Security posture**: "checked" names are not proofs. Each vendored function needs a local contract, positive/negative tests and adversarial coverage before it is called complete (`docs/libc/DEPENDENCIES.md` adoption rules). Upstream advisories are not a substitute for local evidence.
7. **Legal exclusions**: at least one candidate record (Cake) carries a GPLv3 + AI-training addendum, incompatible with this MIT project. Blind copying would import that risk.
