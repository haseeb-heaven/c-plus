## 3. Checked-layer mapping completeness

**[SIBLING RESULT]** `tests/abi/stdc_mapping/RESULTS.md`, compiler
`/usr/bin/clang` Apple clang 16, `-O1 -std=c11`; reproduction:

* **16 ordinary names:** `malloc`, `calloc`, `realloc`, `free`, `memset`,
  `memcpy`, `memmove`, `memcmp`, `strcpy`, `strncpy`, `strcat`, `strncat`,
  `fread`, `fwrite`, `printf`, `fprintf` — **16 PASS, 0 FAIL**.
* **Valid-input parity:** all 16 valid cases print identical stdout in plain
  and checked builds, with build rc `0/0` and run rc `0/0`.
* **Invalid-input refusal:** all 16 hostile checked cases `REFUSED` with exit
  `70`; the plain controls show `NO-PROTECTION` output or abnormal exits
  (`133`, `134`, `139`) — behavioral difference, not ABI difference.
* **Symbol provenance:** all 30 checked targets audited with `nm` are defined
  `T`/`D`/`B` symbols in `libcplus_safecrt.a` or `libcplus_hardened.a`
  (`malloc_s`, `cplus_memset_s_auto`, `cplus_printf`, the `_bounded` and
  `_s_auto` families, the two `_cplus_sc_upstream_*` exports, …).
* **No interposition:** `nm -u` probes show a TU without the header still
  relocates `_malloc` (forbidden `_malloc_s` absent); with the header it
  relocates `_malloc_s` (forbidden `_malloc` absent); `CPLUS_SAFE_C_DISABLE`
  restores `_malloc`; a precompiled `libprecomp.a` still references `_malloc`;
  unmapped ordinary names (`fopen`, `fclose`, `strlen`, `strnlen`) stay on the
  host symbol; a linked plain+checked binary prints `tu_isolation:ok`.
* **Mechanism and limits:** the rewrite is a compile-time `#undef`/`#define`
  in the including TU only. Source-level limits documented in
  `docs/libc/SAFE_C_ORDINARY_MAPPING.md` still apply (e.g. `strlen`/`strnlen`/
  `fopen`/`fclose` are deliberately *not* mapped; some `_auto` macros cast the
  result to `void`; `memcmp` refusal returns the sentinel `-1`; unknown
  capacity is never presented as verified capacity).

`cplus_runtime_set_violation_trap(0)` to print all 64 cases; the production
default trap (exit 70) is unchanged. Each plain hostile case runs in a
`fork()`ed child so corruption cannot reach the supervisor.

## 11. Explicit non-claims

1. **No Rust equivalence.** Matching `OK`/`REFUSED`/`CANARY_OK` tokens on a
   fixed case set are behavioral correspondences only. The broader Rust
   aggregate is not green (29 BLOCKED, 2 BAD_REPORT, exit 1); no equivalent
   safety guarantee, functional equivalence, or performance equivalence is
   claimed.
2. **No 100% memory-safety proof.** The checked layer is runtime constraint
   checking with caller-derived capacities: unknown-capacity policy, bounded
   free/stream caches, and generation checks are heuristics, not proofs of
   provenance, ownership, lifetime, or alias safety. Raw aliases, stale
   pointers, untrusted formats, foreign/raw-`malloc` pointers, arbitrary C
   UB and non-local exits remain outside the guarantee. Passing canaries on
   64 hostile cases is evidence for those cases only.
3. **No platform claim beyond macOS arm64 / Apple clang 16.0.0 / C+ 0.1.0**
   (plus Rust 1.100.0 for the token comparison). macOS x86_64, Linux
   (glibc/musl), Windows (MSVC/UCRT, x86/x64), other clang versions and
   other optimizers are **UNTESTED**; nothing here predicts their layouts,
   calling conventions, or symbol behavior.
4. **No C++ mangled-ABI claim.** Only C-linkage/plain-C symbols are audited;
   the positive observation is limited to "0 `_Z`/`__Z` symbols found".
   No Itanium/MSVC C++ ABI, class-layout, or exception-ABI stability is
   claimed.
5. **No ASan pass.** AddressSanitizer (and Leak/Thread/Memory/CFI) is
   **unsupported by the selected backend** (`error: sanitizer '…' is not
   supported by the selected backend`); host Apple clang 16 ASan also aborts
   at startup even for `int main(){return 0;}`. No pass is claimed for any of
   those configurations. The only sanitizer evidence above is UBSan on the
   checked harness (0 reports) and it is not a substitute for ASan.
6. **External `CPLUS_EXIT_ARITHMETIC` blocker remains unresolved.** Sanitized /
   instrumented C+ runtime builds fail in the *external*
   `c-plus-core/runtime/cplus_runtime.c:129:23` with `error: use of undeclared
   identifier 'CPLUS_EXIT_ARITHMETIC'`, while this checkout's
   `runtime/include/cplus/cplus.h` enum ends at `CPLUS_EXIT_IO = 109`. It is
   owned by `c-plus-core`, out of scope here, and all green results above use
   non-instrumented paths. See `docs/abi/external_blocker_evidence.md` and
   `docs/stdlib/AGENT1_EXTERNAL_RUNTIME_BLOCKER.md`.
7. **No blanket "all green" claim.** The ABI/mapping/safety/consumer/SDK
   groups above are green in their own scope; the broader repo suites and the
   Rust aggregate are not (see §6 and `docs/FINAL_ABI_SAFE_DELIVERY.md`).
8. **No ABI change was made to obtain these results.** The safety layer is
   additive/`static inline`/macro-only at the call site; no public struct
   layout, existing exported-symbol name, function signature, or calling
   convention was edited. Evidence shows the checked subset *matched its
   expectations* on this toolchain; it does not prove future edits cannot
   break the ABI.

---

**Bottom line:** on macOS arm64 / Apple clang 16, the standard-C ABI is
preserved at every measured layer — source blobs, fingerprint, layouts,
signatures, symbols, precompiled archives, consumers and installed SDK — while
the opt-in checked layer converts the tested hostile inputs from raw-C
corruption/crashes into refusals with intact canaries, without any claim of
Rust equivalence, complete memory safety, sanitizer coverage, or
cross-platform validity.
