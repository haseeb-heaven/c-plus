# Checked-CRT I/O examples: C original vs safe-Rust equivalent

Scope: the 7 checked-CRT I/O examples in `examples/crt/`. For each one this
directory contains a standalone, **safe** Rust equivalent (`<name>.rs`) and a
comparison driver (`compare.sh`). All generated artifacts stay in
`benchmarks/example_rust_compare/crt_io/.build/` (text logs retained; compiled
binaries removed after the run and regenerated by `compare.sh`).

## Exact commands

Run everything from the repository root:

```sh
cd /Users/haseeb-mir/Documents/Code/Cpp/c-plus-stdlib
sh benchmarks/example_rust_compare/crt_io/compare.sh
```

Per-example C build (the task recipe, plus the required `-Istdlib/safe`):

```sh
cd <repo-root>
/usr/bin/clang -std=c99 \
  -Ilibc/install-include \
  -Ithird_party/safeclib/include \
  -Istdlib/safe \
  examples/crt/<name>.c \
  build/libc/libcplus_hardened.a \
  build/safe/libcplus_safecrt.a \
  -o benchmarks/example_rust_compare/crt_io/.build/orig_<name>
```

Notes on the C command:
- The recipe in the task listed `-Ilibc/install-include -Ithird_party/safeclib/include`
  and "both archives". With only those two include directories the compile
  fails with `examples/crt/fopen_s.c:2:10: fatal error: 'safe_io.h' file not found`,
  because `safe_io.h`, `safe_format.h` and `safe_error.h` live in
  `stdlib/safe/`. That include path was therefore added.
- "Both archives" were taken as `build/libc/libcplus_hardened.a` and
  `build/safe/libcplus_safecrt.a`. The checked I/O symbols (`cplus_fopen_s`,
  `cplus_fclose_s`, `cplus_fread_s`, `cplus_fwrite_s`, `cplus_fprintf_s`,
  `cplus_fscanf_s`) resolve from `libcplus_safecrt.a`; verified that the
  hardened archive alone leaves them undefined and that the safecrt archive
  alone links. Both are supplied as specified.

Per-example Rust build:

```sh
rustc -O benchmarks/example_rust_compare/crt_io/<name>.rs \
      -o benchmarks/example_rust_compare/crt_io/.build/rust_<name>
```

Per-example run and comparison:

```sh
timeout 30 .build/orig_<name> > .build/orig_<name>.stdout 2> .build/orig_<name>.stderr
orig_exit=$?
timeout 30 .build/rust_<name> > .build/rust_<name>.stdout 2> .build/rust_<name>.stderr
rust_exit=$?
# MATCH iff exit codes are equal and stdout files are byte-identical (cmp -s).
```

A static gate in `compare.sh` rejects any Rust source containing an `unsafe`
block, `unsafe fn`, `extern "C"`, or `#[link(...)]`. All 7 sources pass it.

## Comparison criterion

`MATCH` means: identical process exit code **and** byte-identical stdout.
stderr was captured for evidence and was empty for all 14 runs (0 bytes each).
No refusal/error branch of the checked APIs is exercised by these 7 examples
— they are all success paths — so the `Result`/`Option` refusal models in the
Rust helpers are documented, not verified by these runs.

## Explicit non-equivalence statement

**These Rust programs are NOT behaviorally equivalent to the checked-CRT C
examples in the general API sense. They are equivalent only with respect to
the observable success-path behavior measured here (stdout bytes and process
exit code), which is what the 7 examples happen to exercise.** The following
differences are real and are *not* established as equivalence by this comparison:

1. **No runtime checked-CRT machinery.** The C library performs constraint
   handling, violation logging, statistics recording and global stream
   tracking (`cplus_safe_log`, `cplus_safe_stat_record`, closed/live stream
   tables). The Rust equivalents use plain std I/O and have none of these
   side effects. Those side effects are not observable in these examples'
   stdout/exit, but would be observable through the C library's log/stat APIs.
2. **Double-close protection differs in mechanism.** C detects and refuses a
   second `fclose_s` at runtime via a tracked table; Rust cannot double-close
   at all because ownership consumes the `File`. The safety property is
   comparable, the mechanism and error behavior are not.
3. **Bounded-I/O parameters are not the same API.** C's `bmax` is an explicit
   runtime argument used to clamp `count`; Rust's bound is the slice length.
   The C `_s` helpers also return 0 for null pointers — a condition with no
   representation in safe Rust. Zero-size/count refusals are modelled as
   `Ok(0)` but are never exercised by these examples.
4. **Format-string safety is compile-time in Rust, runtime in C.** The C
   checked formatters refuse non-literal format strings, `%n` (all length
   forms), and unbounded `%s`/`%[...]` at runtime. Rust's `write!` validates
   at compile time and the scanner has no format string at all, so those
   refusal paths are *unrepresentable*, not reimplemented. This is a stronger
   static guarantee, not a matching runtime behavior.
5. **`scanf_s` example does not test `scanf_s`.** Both programs only print a
   fixed line; neither reads stdin. Any claim about stdin scanning equivalence
   is unsupported by this example.
6. **Temp-file locations differ.** The originals hard-code `/tmp/cplus_*.tmp`;
   the Rust programs use `std::env::temp_dir()` with fixed file names. Both are
   bounded and contain no user-specific path, but they are different files.
   File contents written by `fwrite_s`/`fprintf_s`/`fscanf_s` are removed by
   the programs and were not compared directly — only the programs' internal
   pass/fail checks (which drive stdout/exit) were compared.
7. **Refusal models are untested.** `Result`/`Option` branches modelling
   fopen/fclose/read/write/format refusals exist in the Rust sources but are
   not triggered by any of these 7 success-path examples. Their equivalence to
   the C error codes is asserted by inspection of `stdlib/safe/src/safe_io.c`
   and `safe_format.c`, not demonstrated by execution.

Consequently, `MATCH` for all 7 examples should be read as "the Rust port
produces the same observable output and exit status as the original for its
documented success path", **not** as "the Rust port is a drop-in replacement
for the checked CRT".
