## Exact commands used

Rebuild and compare everything (one command):

```sh
cd /Users/haseeb-mir/Documents/Code/Cpp/c-plus-stdlib
timeout 300 sh benchmarks/example_rust_compare/demos_a_d/compare.sh
```

For each `name` in `A_hello B_bounds C_resource D_class`, `compare.sh` runs:

```sh
timeout 30 ./build/c+ build --strict --sanitize=none \
    demos/<name>.c -o out/orig_<name>
timeout 30 rustc -O <name>.rs -o out/rust_<name>
timeout 30 out/orig_<name> >out/orig_<name>.stdout 2>out/orig_<name>.stderr
timeout 30 out/rust_<name>  >out/rust_<name>.stdout  2>out/rust_<name>.stderr
```

Both runs are wrapped in a `{ ...; rc=$?; } 2>/dev/null` group so the shell's
own "Abort trap" job message for the intentionally-aborting B_bounds process
does not pollute the report. See `compare.sh` for the literal commands. All
four programs terminate well within 30 s.

### Why the C+ compiler, not plain clang

The task text suggests plain `/usr/bin/clang -std=c99` for `.c` files. That
works for `A_hello.c` and `B_bounds.c` (both are C99 syntax), but
`C_resource.c` uses the C+ `resource struct` extension and `D_class.c` uses
the C+ `class` extension, which clang cannot parse. Moreover,
`demos/run_demos.sh` compiles **all** demos (including `.c` ones) with
`build/c+`, and the task note states these are C+ language demos. Therefore
`build/c+` is the supported build for all four originals; using one compiler
keeps the comparison consistent. The documented safe-mode flag set
`--strict --sanitize=none` builds all four successfully.

With `--sanitize=none`, demo B still aborts: the diagnostic comes from the
C+ checked-index runtime helper, not from UBSan. The default (instrumented)
`./build/c+ build demos/A_hello.c` currently **fails** in this checkout
(`/Users/haseeb-mir/Documents/Code/Cpp/c-plus-core/runtime/cplus_runtime.c:144:
use of undeclared identifier 'CPLUS_EXIT_ARITHMETIC'`, exit 1), i.e. an
unrelated runtime source/header mismatch in a sibling worktree. That is why
the explicit `--strict --sanitize=none` build was used; it is a documented
safe mode and does not change any of the four programs' observable stdout.

### B_bounds — DIFFERENT

```
orig stdout: b'valid: 30\n'
rust stdout: b'valid: 30\n'          # identical: final line absent in both

orig stderr: b"C+ error: index 9 is outside the bounds of 'samples' (length 4)\n"
rust stderr: b"\nthread 'main' (<pid-dependent thread id>) panicked at .../B_bounds.rs:18:29:\nindex out of bounds: the len is 4 but the index is 9\nnote: run with `RUST_BACKTRACE=1` environment variable to display a backtrace\n"
exit: orig 134 (SIGABRT)             rust 101 (panic)
```

Exact differences, itemised:

1. Both print `valid: 30` and neither prints `this line must not be reached`
   — the **observable control-flow behavior matches**.
2. Diagnostic wording differs: C+ says
   `C+ error: index 9 is outside the bounds of 'samples' (length 4)`; Rust
   says `index out of bounds: the len is 4 but the index is 9`.
3. C+ writes the diagnostic with no leading blank line; Rust's panic starts
   with a leading `\n` and adds `thread 'main' (...) panicked at <abs path>:<line>:<col>:`
   plus a `RUST_BACKTRACE` hint line. The Rust panic text embeds the absolute
   source path, line/column and a **run-specific thread id**, so its stderr is
   not byte-stable across runs. This is a genuine Rust runtime diagnostic; it
   was not rewritten to imitate the C+ message.
4. Exit status differs: 134 (SIGABRT, C+ fail-fast) vs 101 (Rust `panic`).

### C_resource — MATCH

```
orig stdout: b'normal return\nclose log\nrun(0)=0\nearly return\nclose log\nrun(1)=1\n'
rust stdout: b'normal return\nclose log\nrun(0)=0\nearly return\nclose log\nrun(1)=1\n'
orig stderr: b''                     rust stderr: b''
```

Both orderings are non-trivial and were verified: `run(...)` is evaluated

## Non-equivalence statement (matching output ≠ equivalent safety guarantees)

A `MATCH` here means only that stdout, stderr and exit status were identical
for these specific, deterministic inputs. It does **not** mean the two
programs provide the same safety guarantees:

- **Where the check happens.** Rust enforces slice bounds, borrow exclusivity
  and null-representability at compile time; a `&mut Player` cannot alias
  another borrow, whereas the C+ `Player *view` is a raw pointer. The C+
  examples rely on compiler analysis plus runtime checks (here the checked
  index helper) inserted into generated C; Rust's panic in B is a language
  runtime check on a value made opaque with `std::hint::black_box`.
- **B is deliberately DIFFERENT.** The C+ diagnostic and SIGABRT were not
  reproduced because fabricating that text with `eprintln!` + `abort()` would
  not be an idiomatic safe-Rust equivalent. The Rust program really panics on
  an out-of-range index; its message and exit code are Rust's own.
- **RAII mechanisms differ.** C+ lowers `resource struct` + `File_drop` into
  explicit cleanup calls; Rust uses a compiler-inserted `Drop`. `Option<File>`
  makes the NULL `FILE *` state explicit, but the C runtime's `fclose` error
  behavior, buffering and diagnostics are not modelled.
- **No general safety claim.** None of these four small examples demonstrates
  or proves memory safety of either language. In particular, a matching C+
  outcome does not establish equivalence of allocator behavior, sanitizer
  coverage, integer-overflow policy or pointer-arithmetic checks.
