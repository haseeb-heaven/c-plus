# json_log runnable examples — exact commands, evidence, results

Branch: `agent/modern-stdlib`. Everything below was run from the repository
root. Only files in `benchmarks/rust_examples/json_log/` were created.

## Files

| File | Role |
| --- | --- |
| `json_log.rs` | Safe-Rust analogue examples. No `unsafe`, no FFI, `str` methods + `Vec<String>`. |
| `harness.c` | C+ harness. Calls the real compiled checked symbols plus the static-inline `json.hp`/`log.hp` APIs. |

## Symbol verification (nm, both archives)

`nm` was run against the two archives used by the existing Rust-vs-C+ harness
(`tests/rust_vs_cplus/run_compare.sh`):

```sh
nm -g build/safe/libcplus_safecrt.a | grep -E 'cplus_(json|safe_log)'
nm -g build/libc/libcplus_hardened.a | grep -E 'cplus_libc_log'
```

Defined (`T`) symbols — exact output:

```
# build/safe/libcplus_safecrt.a
0000000000000000 T _cplus_json_parse
00000000000001b0 T _cplus_json_get_int
00000000000002ac T _cplus_json_get_str
0000000000000140 T _cplus_json_free
0000000000000000 T _cplus_safe_log_set_level
0000000000000010 T _cplus_safe_log_get_level
0000000000000020 T _cplus_safe_log

# build/libc/libcplus_hardened.a
0000000000000000 T _cplus_libc_log_set_enabled
0000000000000018 T _cplus_libc_log
```

`compare.sh` re-checks exactly these nine symbols on every run and writes the
raw `nm` output to `benchmarks/rust_examples/json_log/.out/nm_evidence.txt`.
If any is absent it emits `BLOCKED ...` plus the evidence path and reports
`blocked=18` (the full protocol line count) instead of fabricating a result.

### Naming note (important)

There is **no** compiled symbol with the literal prefix `cplus_log_`:

```sh
nm -g build/safe/libcplus_safecrt.a build/libc/libcplus_hardened.a \
  | grep -E ' T _?cplus_log_'      # -> (none)
```

The compiled logging entry points are `cplus_safe_log{,_set_level,_get_level}`
(declared in `stdlib/safe/safe_log.h`, defined in `stdlib/safe/src/safe_log.c`)
and `cplus_libc_log{,_set_enabled}` (declared in `libc/log/log.h`, defined in
`libc/log/log.c`). `cplus_log` itself is only a macro in
`runtime/include/cplus/cplus.h`. The `cplus_json_*` functions are compiled in
`w_safe_json.o` inside `libcplus_safecrt.a`; the repository ships no header for
them, so `harness.c` declares their prototypes locally.

### Recovered `cplus_json_*` prototypes

Recovered from `nm` + `otool -tV build/safe/w_safe_json.o`, then confirmed by a
link-and-run probe against `libcplus_safecrt.a` (parse/good → handle + status 0;
parse/truncated → NULL + status 2; parse/NULL → NULL + status 1;
get_int("n") → 1, 42; get_str("name") → "alpha"; free/free(NULL) → no crash):

```c
void       *cplus_json_parse(const char *text, int *status);
                                    /* status 0=ok, 1=null input, 2=parse fail */
int         cplus_json_get_int(void *handle, const char *key, int64_t *out);
const char *cplus_json_get_str(void *handle, const char *key);
void        cplus_json_free(void *handle);
```

## APIs and cases

Eight API names, six case labels, 18 emitted lines (all deterministic):

| API | Source | Cases / tokens |
| --- | --- | --- |
| `cplus_json_parse` | compiled safecrt | valid `OK`, malformed `REFUSED`, null_args `REFUSED` |
| `cplus_json_get_int` | compiled safecrt | valid `OK`, null_args `REFUSED` |
| `cplus_json_get_str` | compiled safecrt | valid `OK`, null_args `REFUSED` |
| `cplus_json_free` | compiled safecrt | valid `OK`, null_args `OK` (documented no-op) |
| `json_parse_budget` | static-inline `stdlib/json.hp` | valid `OK`, budget `REFUSED`, null_args `REFUSED` |
| `cplus_safe_log` | compiled safecrt (+ `get_level`) | write_read `OK`, null_stream `OK` |
| `cplus_libc_log` | compiled hardened libc | write_read `OK`, null_stream `OK` |
| `log_sink` | static-inline `stdlib/log.hp` | write_read `OK`, null_stream `REFUSED` |

Case labels: `valid`, `malformed`, `budget`, `null_args`, `write_read`,
`null_stream`.

Fixtures (identical in both programs, no wall-clock/randomness):
`GOOD = {"name":"alpha","n":42,"ok":true}`,
`MALFORMED = {"name":"alpha","n":`, `DEEP` = 32 nested `[`/`]` around `0`.
`json_parse_budget` uses depth budget 8; the Rust analogue uses depth 8 and
length 256. Logging is checked via observable state only —
`cplus_safe_log_get_level()` (write/read), preserved `errno` (`cplus_libc_log`
documents that it restores `errno`), and a closed fd 2 for the null-stream
path. `log_sink` is queried with `valid()`/`level()` only; its `write()` (which
would introduce a wall-clock timestamp) is never called. Harness logging
diagnostics go to stderr, which `compare.sh` discards; fd 2 is restored after
the closed-stream test.

## Exact commands and real results

Build/run via the comparison driver (this is the canonical verification):

```sh
sh benchmarks/rust_examples/json_log/compare.sh
# RUST_EXAMPLES json_log 8 6 18 0 0
# exit 0
```

Equivalent individual commands (from the repo root):

```sh
mkdir -p benchmarks/rust_examples/json_log/.out

./build/c+ build benchmarks/rust_examples/json_log/harness.c \
  --default --sanitize=none -I. -Ithird_party/yyjson \
  -Lbuild/ext -lyyjson \
  -o benchmarks/rust_examples/json_log/.out/harness \
  -- build/safe/libcplus_safecrt.a build/libc/libcplus_hardened.a

rustc --edition 2021 benchmarks/rust_examples/json_log/json_log.rs \
  -o benchmarks/rust_examples/json_log/.out/json_log

benchmarks/rust_examples/json_log/.out/harness 2>/dev/null
benchmarks/rust_examples/json_log/.out/json_log 2>/dev/null
diff -u <(harness 2>/dev/null) <(json_log 2>/dev/null)   # empty
```

Observed 18/18 matched, 0 mismatched, 0 blocked; `diff.txt` is empty. The C+
driver emits four benign `-Wunused-command-line-argument` warnings because the
same `-lyyjson`/archive arguments are visible to its intermediate compile
step; linking and execution succeed. The Rust build is warning-free.

BLOCKED path check (override to a missing driver):

```sh
CPLUS_BIN="$PWD/build/does-not-exist" sh benchmarks/rust_examples/json_log/compare.sh
# BLOCKED C+ driver not executable: ... (override with CPLUS_BIN)
# RUST_EXAMPLES json_log 8 6 0 0 18
# exit 0
```

Budget-case cross-check: the 32-deep fixture parses successfully with raw
yyjson (`yyjson_read_opts` → `yyjson_deep_valid=1`), so the C-side
`json_parse_budget budget REFUSED` token is caused by `json.hp`'s pre-parse
budget check (max_depth 8), not by a yyjson syntax error. The compiled
`cplus_json_parse` has no depth/length budget of its own (vendored yyjson
ships `YYJSON_READER_DEPTH_LIMIT == 0`), which is why the budget case uses the
header-only `json_parse_budget` API instead.

## Non-equivalence statement

Matching tokens are evidence about these fixed examples only. They do **not**
prove that the safe-Rust code and the C+/C checked APIs are semantically,
memory-safety- or performance-equivalent. In particular:

* `json_log.rs` never calls the archives; it is a safe-Rust *pattern* example
  (hand-written checker + `Vec` logger) that happens to produce the same
  outcome tokens on the chosen fixtures. It is not an FFI wrapper and provides
  no proof about the C ABI, lifetimes or allocator behaviour.
* The C side calls the real compiled `cplus_json_*`/`cplus_safe_log*`/
  `cplus_libc_log*` symbols, but its budget and sink lines come from
  static-inline C+ headers (`json.hp`, `log.hp`) that have no compiled symbol.
* Outcome equality for `OK`/`REFUSED` says nothing about the mechanism behind
  the refusal (borrow checker vs. status code vs. `error` value), nor about
  behaviour on inputs outside these fixtures.
