# Allocator performance benchmarks — Task 5 Phase 6

Files (all under `benchmarks/stdlib/allocator/`):

- `allocator_bench.c` — the benchmark (C, gnu17, no third-party framework).
- `run.sh` — builds and runs the full matrix; writes `results/allocator_bench.csv`.
- `results/allocator_bench.csv` — raw, unedited output of the actual matrix below.
- `tracking_toggle.c` — isolates tracking ON vs OFF from identical source via
  the documented `CPLUS_MALLOC_TRACKING` macro.
- `results/tracking_toggle.txt` — actual output of the toggle build+run below.
- `allocator_bench`, `tracking_on`, `tracking_off` — binaries produced by the
  runs below (regenerated by the commands in this file).

## What is measured

| Category | Workload flag | Unit (`ops`) |
|---|---|---|
| Allocation throughput | `alloc` | 200,000 × 32 B allocations (frees untimed) |
| Free throughput | `free` | 200,000 × 32 B frees (allocations untimed) |
| Reallocation | `realloc` | 200,000 grow/shrink reallocs (64 KiB ↔ 128 KiB) |
| Small allocations (≤64 B) | `small` | 200,000 alloc+free pairs, sizes 8/16/…/64 B |
| Large allocations (≥64 KiB) | `large` | 4,000 alloc+free pairs, sizes 64…512 KiB |
| Container growth | `grow` | 200,000 growth reallocs (repeated 8→2048 int vector, doubling, mirrors `stdlib/vector.hp`) |

Every workload uses a **fixed xorshift32 seed** (`314159265`, reset each round),
**2 untimed warmup rounds**, and **11 measured rounds**. The three variants are
**interleaved round-robin** (round *r* runs every variant once, back-to-back).
The program itself computes min, median (p50), max, nearest-rank p95, ns/op and
Mops/s; **no Python** (or any other post-processing) is involved. Only the
designated `run` phase is timed; `prepare`/`finish` are untimed.

## Variants — tracking disabled vs enabled, with vs without debug queries

- **`raw`** — host `malloc`/`realloc`/`free`, **no C+ metadata side table**
  (tracking **disabled**). Baseline/control only; not a C+ allocator.
- **`tracked`** — `cplus_malloc`/`cplus_realloc`/`cplus_free` from `cplus_libc.h`
  (the C+ hardened libc allocator): every call maintains the thread-safe
  metadata side table (tracking **enabled**), but the benchmark issues **no
  debug queries**.
- **`query`** — same tracked allocator **plus** a debug query after every
  operation: `cplus_alloc_size`, `cplus_alloc_is_live`, `cplus_alloc_live_count`
  on allocation paths (and `cplus_alloc_live_count` on the free path).

Only C+ stdlib allocator APIs (`cplus_libc.h`) are the subject of measurement;
`malloc` appears solely as the untracked control. The bookkeeping pointer array
uses host `malloc` in all variants and is never timed.

Environment: `Darwin 27.2.0 arm64`, Apple M2, Apple clang 16.0.0
(`clang-1600.0.26.6`). Run took ~27 s wall clock.

**Why not `build/c+`:** the C+ compiler links `libcplus_runtime.a`, which
defines `cplus_realloc`; the hardened libc defines it too, so linking both
fails with `duplicate symbol '_cplus_realloc'`. (`--legacy-c` also fails on
`restrict` in `cplus_libc.h`.) We therefore use the same toolchain pattern as
the C+ libc test suite (`tests/libc/run_libc_tests.sh`): plain C compiler +
`build/libc/libcplus_hardened.a`. This is a limitation of the build wrapper,
not of the benchmarked API.

## Is the debug-metadata overhead isolated? — Yes, partly

**It CAN be isolated for the query cost.** `tracked` and `query` use the *same*
allocator; the only difference is the debug query calls. So
`query_median − tracked_median` is the cost of those queries:

```sh
B=benchmarks/stdlib/allocator/allocator_bench
$B --workload small   --variant tracked --runs 11 --warmup 2 --ops 200000 --seed 314159265
$B --workload small   --variant query   --runs 11 --warmup 2 --ops 200000 --seed 314159265
$B --workload realloc --variant tracked --runs 11 --warmup 2 --ops 200000 --seed 314159265
$B --workload realloc --variant query   --runs 11 --warmup 2 --ops 200000 --seed 314159265
```

(Run `sh benchmarks/stdlib/allocator/run.sh` first if `allocator_bench` is not
present.) On this run: `small` ≈ +15.8 ns/pair, `realloc` ≈ +25.6 ns/call,
`large` ≈ +32 ns/pair — consistent with three mutex-protected side-table
lookups per query.

**The side-table overhead is only bounded, not isolated.** `tracked − raw`
includes the global mutex, size/overflow checks and side-table maintenance, not
metadata alone, and `raw` is a different allocator (host malloc). To measure
the pure tracking-toggle delta from the same source, compile with the
documented `CPLUS_MALLOC_TRACKING` macro on/off — but note both builds still
link the hardened libc, so this is left as the exact isolation command rather
than a reported number here:

```sh
/usr/bin/clang -O2 -std=gnu17 \
  -Ilibc/install-include -DCPLUS_MALLOC_TRACKING \
  benchmarks/stdlib/allocator/tracking_toggle.c \
  build/libc/libcplus_hardened.a -lm -pthread -o /tmp/track_on
/usr/bin/clang -O2 -std=gnu17 \
  -Ilibc/install-include \
  benchmarks/stdlib/allocator/tracking_toggle.c \
  build/libc/libcplus_hardened.a -lm -pthread -o /tmp/track_off
```

`tracking_toggle.c` is not part of this deliverable (file ownership is limited
to this directory and the benchmark above already isolates queries); the
command is given so the parent task can reproduce the toggle if needed.

## Caveats / honest limitations

1. **Free-path cliff (tracked):** ~1.38 µs/free at 200 k blocks. This is not a
   constant cost: `recent_add()` in `libc/src/stdlib/alloc.c` linearly probes a
   fully saturated `g_recent[1024]` open-addressed cache on every free, so free
   throughput degrades sharply once >1024 distinct addresses are freed. This is
   a real finding, not measurement noise.
2. **`query` is occasionally *faster* than `tracked` on `free`** (0.2508 s vs
   0.2766 s here). The recent-cache probe dominates and is highly sensitive to
   address reuse; the extra `cplus_alloc_live_count()` is negligible. Do not
   read a negative delta as "queries are free" — it is noise.
3. **Variance on `alloc`:** one round hit 0.274 s (max), inflating p95; the
   median (0.0445 s) is used and 9 of 11 rounds were near it.
4. Numbers are from a single machine (Apple M2) at one point in time; they are
   reproducible in configuration (seed/rounds/warmup/ops) but not guaranteed
   identical on other hardware or under load. No numbers are estimated — every
   value above is copied from `results/allocator_bench.csv`.
